# devlens-rules

SDK and framework detection rules for DevLens, an on-device APK/AAB inspector for Android.

The app ships a copy of these rules and checks this repo once a day, on an unmetered network only. It reads:

```
https://raw.githubusercontent.com/nguynduyanh169/devlens-rules/main/v1/rules_latest.json
https://raw.githubusercontent.com/nguynduyanh169/devlens-rules/main/v1/<file from the manifest>
```

## Layout

| Path | What it is |
|---|---|
| `v1/rules_latest.json` | Manifest: `schemaVersion`, `version`, `publishedAt`, `file`, `size`, `sha256` of the current rules db |
| `v1/rules-<version>.db` | SQLite rules db, schema v1. The file name carries the version and never changes once published |
| `src/schema.sql` | Schema v1 of the rules db |
| `src/rules.sql` | Rules, matchers, the `hermes-version` table and the `meta` rows (`version`, `published_at`) |
| `src/dart-snapshots.csv` | The `dart-snapshot` ledger (below); `build.sh` turns it into the `dart-snapshot` rows |
| `build.sh` | Builds the db from `src/` and writes `v1/` |
| `tools/` | Python 3 (stdlib only) used by `build.sh` and the workflow; tests in `tools/tests/` |
| `.github/workflows/dart-snapshots.yml` | The daily action that adds new Flutter releases to the ledger |

`v1/` matches `schemaVersion` 1. A schema change is published under `v2/`; apps that only read v1 keep reading `v1/`.

The app uses a download only if its size and SHA-256 match the manifest, its schema passes the reader's checks, and its `version` is higher than the bundled one.

## Publishing

Every file in `v1/` is generated by `build.sh`. Don't edit them by hand. Versions only go up: a bad publish is replaced by a higher version, never by rewriting an old one. `build.sh` refuses to overwrite a published `rules-<version>.db` with other bytes.

**By hand** (any rule, `hermes-version`, a ledger fix):

1. Edit `src/`, raise `version` and set `published_at` in the `meta` rows of `src/rules.sql`.
2. Run `bash build.sh` (needs `python3`, `sqlite3`, `shasum`). `OUT_DIR=<dir> bash build.sh` builds somewhere else, to check without touching `v1/`.
3. Commit `src/` and `v1/` together, in one PR, and merge it.

**Automatically** (`dart-snapshot`): merge the PR the action opens on `auto/dart-snapshots`.

The db and the manifest land in the same commit, so the old "push the db before the manifest" rule no longer holds. If the raw CDN serves the new manifest before the new db, the app sees a 404 or a size/SHA-256 mismatch and tries again on its next daily check.

DevLens bundles a copy of the latest published db: run `bash rules/sync.sh` in DevLens before a release.

Running the tools' tests: `python3 -m unittest discover -s tools/tests -t .` from the repo root.

## dart-snapshot

The `dart-snapshot` table maps the Dart snapshot hash of a Flutter `libapp.so` to the Flutter minor (`M.m`) that built it. DevLens shows that version and derives Impeller vs Skia from it, so a value is always `M.m`: never a patch version, never a range.

`src/dart-snapshots.csv` holds one row per Dart SDK version (the raw `dart_sdk_version` of Flutter's `releases_linux.json`, the data behind <https://docs.flutter.dev/install/archive>):

| Column | Meaning |
|---|---|
| `dart_version` | Raw `dart_sdk_version`, e.g. `3.13.7` or `3.10.0 (build 3.10.0-290.4.beta)` |
| `flutter_version` | The Flutter release built to read the hash; the table value is its `M.m` |
| `release_date` | That release's date |
| `hash` | 32 characters `[0-9a-f]`, or empty: looked at and skipped on purpose (no row, never built again) |

Rows with the same hash and the same minor give one table row. A hash that two minors share stops `build.sh`: fix the ledger by hand.

The first three rows (Flutter 3.27.4, 3.29.3, 3.32.8) were checked by hand against `gen_snapshot` and the `libapp.so` each builds; only one patch release of each minor was checked. Every other row comes from the action.

**The action** (`dart-snapshots.yml`, daily at 03:23 UTC, or *Run workflow* in the Actions tab):

1. Reads `releases_linux.json` and keeps the stable releases from Flutter 3.27 on that name a Dart SDK. For each Dart SDK version not in the ledger on `main`, it picks the earliest Flutter release that shipped it.
2. Builds a hello-world app with that release (`flutter build apk --release --target-platform android-arm64`, JDK 17), reads the hash from `lib/arm64-v8a/libapp.so`, and checks that `lib/arm64-v8a/libflutter.so` of the same APK holds the same string.
3. Adds the rows to the ledger, raises `version`, sets `published_at`, runs `build.sh`, and opens or updates the PR on `auto/dart-snapshots`. The PR body lists every new row, failed build and conflicting hash.

A run is red when a build failed or a hash conflicts. The PR still holds every successful row, and a failed Dart version is tried again the next day; to stop retrying one, add its ledger row with an empty `hash` by hand. Hashes already on an open PR are reused, not rebuilt, and a run with nothing new leaves the PR alone.

**One-time setup:** Settings → Actions → General → Workflow permissions → tick *Allow GitHub Actions to create and approve pull requests*. The workflow re-enables itself on every run so that GitHub does not disable the schedule after 60 days without commits; if it is disabled anyway, enable it again in the Actions tab.
